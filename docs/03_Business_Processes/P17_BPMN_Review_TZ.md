# П17. Проверка BPMN схемы, отладка и ТЗ

## 1. Проверка и верификация BPMN схемы

* **Синтаксическая проверка:** Все потоки сообщений (Sequence Flows) имеют начало и конец. Каждая развилка (Gateway) имеет четкие условия выхода.
* **Семантическая проверка:** * Событие `ItemReceived` корректно инициирует расчет нагрузки.
    * Событие `OverloadDetected` имеет обработчик на стороне фронтенда (изменение стейта UI).
    * Путь «Возврат» (`ItemReturned`) учитывает освобождение ячейки хранения.
* **Проверка ролей:** Действия Владельца и Оператора разделены на разные дорожки (Lanes), что соответствует реализации RBAC на бэкенде.

## 2. Процесс отладки (Debugging Strategy)
Отладка системы мониторинга требует проверки как данных, так и времени их обработки.

### 2.1. Backend (Rust/Actix)
- **Tracing:** Использование крейта `tracing` для логирования каждого запроса с указанием `request_id`. Это позволяет отследить путь посылки от лога до БД.
- **Unit-тесты:** Проверка расчетного модуля — подача 100 операций в час при лимите 50 должна гарантированно возвращать статус `Overload`.
- **SQL Debug:** Логирование сырых SQL-запросов через `sqlx-cli` для выявления медленных выборок при генерации отчетов.

### 2.2. Frontend (React/TS)
- **React DevTools:** Проверка рендеринга графиков нагрузки. Убеждаемся, что компонент не перерисовывается лишний раз при каждом тике таймера.
- **Network Mocking:** Тестирование поведения интерфейса при задержке ответа от API (обработка состояний `Loading` и `Error`).

## 3. Финальное ТЗ (Техническое задание)

### 3.1. Цель системы
Автоматизация мониторинга пропускной способности пунктов выдачи заказов и предотвращение критических очередей.

### 3.2. Функциональные требования (FR)
- **FR1:** Регистрация операций (Приемка, Выдача, Возврат).
- **FR2:** Автоматический расчет коэффициента загрузки на основе лимитов ПВЗ.
- **FR3:** Визуальное оповещение о перегрузке (Красная зона).
- **FR4:** Экспорт операционных логов в формате CSV.
- **FR5:** Разграничение прав: Владелец (все ПВЗ), Оператор (только свой ПВЗ).

### 3.3. Нефункциональные требования (NFR)
- **Производительность:** Время отклика API на операцию записи не более 200 мс.
- **Надежность:** Использование транзакций БД для сохранения целостности лога операций.
- **Безопасность:** Передача данных по HTTPS, хранение сессий в Stateless JWT.
- **Локализация:** Поддержка кириллицы в адресах и именах (UTF-8).

### 3.4. Стек технологий
- **Backend:** Rust (Actix-web, SQLx, PostgreSQL).
- **Frontend:** React, TypeScript, Vite, Tailwind CSS.
- **Инфраструктура:** Docker, GitVerse CI/CD.
