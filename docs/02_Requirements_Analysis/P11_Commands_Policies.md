# П11. Выделение команд и политик

## 1. Матрица команд и ролей

### 1.1. Роли пользователей (RBAC)
- **Владелец (Owner)**
    - *Права:* Полный доступ к аналитике всей сети, создание и редактирование ПВЗ, управление настройками пропускной способности.
    - *Цель:* Стратегическое планирование и контроль эффективности.
- **Администратор/Менеджер (Admin)**
    - *Права:* Технический мониторинг, просмотр системных логов и журнала ошибок, управление учетными записями.
    - *Цель:* Поддержание работоспособности и аудит данных.
- **Оператор (Operator)**
    - *Права:* Регистрация операций (приемка, выдача, возврат) в рамках конкретного ПВЗ, просмотр текущего статуса нагрузки.
    - *Цель:* Выполнение ежедневных операционных задач.

### 1.2. Команда разработки
- **Team Lead:** Ответственный за архитектуру, безопасность (JWT/RBAC) и интеграцию компонентов.
- **Backend Developer:** Разработка серверной логики на Rust, работа с БД PostgreSQL, реализация расчетных модулей.
- **Frontend Developer:** Создание интерфейсов для работы с данными, графиков и таблиц на React/TS.
- **Designer / UI-UX:** Проектирование макетов в Figma, разработка дизайн-системы и визуализация аналитики.

## 2. Операционные политики и алгоритмы

### 2.1. Политика детекции перегрузки (Overload Policy)
- **Алгоритм:** Система рассчитывает `load_factor = (текущие_операции / установленный_лимит) * 100%`.
- **Политика оповещения:** При `load_factor > 100%` статус ПВЗ автоматически меняется на «Перегрузка» и подсвечивается красным цветом в интерфейсе.

### 2.2. Политика валидации данных
- **Frontend:** Обязательная проверка типов и обязательных полей перед отправкой запроса.
- **Backend:** Использование `Validator crate` для проверки бизнес-логики (например, невозможность выдачи товара, который не был принят).

## 3. Технические политики (DevOps & Security)

### 3.1. Политика безопасности (Security Policy)
- **Аутентификация:** Использование Stateless JWT. Токены не хранятся в БД сервера, а проверяются на лету через Middleware.
- **Защита данных:** Все запросы к БД проходят через типизированные параметры SQLX для защиты от SQL-инъекций.
- **CORS:** Разрешены запросы только с доверенного домена фронтенда.

### 3.2. Политика разработки (Git & CI/CD Policy)
- **Ветвление:** Основная разработка ведется в ветке `develop`. Слияние в `main` происходит только после успешного прохождения тестов.
- **Автоматизация:** Запрещено слияние Pull Request, если пайплайны в GitVerse Actions (сборка, тесты, линтер) завершились с ошибкой.
- **Контейнеризация:** Использование Multi-stage Docker образов для обеспечения минимального размера и безопасности артефактов.
